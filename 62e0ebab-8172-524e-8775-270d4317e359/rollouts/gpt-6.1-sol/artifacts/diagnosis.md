# Durable sourcing loss during consumer leadership changes

## Defect and evidence

The defect is exposure of **uncommitted consumer delivery sequence numbers under flow control**, compounded by permitting delivery selection during a proposed consumer reset. It is not deletion from the origin or ordinary message-id deduplication.

In `server/consumer.go`, the original `replicateDeliveries` returned false whenever `cfg.FlowControl` was true, even for a replicated, acknowledged durable consumer. `deliverMsg` proposed `updateDeliveredOp`, but immediately put the message on `outq` in that case. Proposing a Raft entry does not mean it has committed. The existing quorum delivery path instead retains the message in `pendingDeliveries`; `applyConsumerMsgOp` in `server/jetstream_cluster.go` releases it when the delivery entry applies. The flow-control exception bypassed precisely this protection.

On leadership acquisition, `readStoredState` / `applyState` restore the agreed delivered state, including the next consumer delivery number. A delivery number sent by the previous leader without quorum can therefore be assigned again, potentially to a different stream sequence. A step-down creates this opportunity; stopping the former leader can remove its uncommitted progress. Restarting it recovers the agreed state, not a guarantee that every externally visible delivery was recorded. CPU contention increases the opportunity for proposals, application and outbound delivery to separate in time. It is not a necessary logical precondition.

The downstream checks explain the unusually diagnostic symptom. `processInboundMirrorMsg` and `processInboundSourceMsg` decode both stream and consumer delivery sequences from the acknowledgement reply subject. Older stream sequences are suppressed, but a duplicate whose delivery number is the expected next number advances delivery accounting. A consecutive consumer delivery number accompanying a jump in upstream stream sequence is treated as legitimate upstream filtering/deletion/expiration. The mirror explicitly calls `skipMsgs` for that range. The source accepts the upstream jump and advances its source position; it does not preserve the origin's sequence numbering as its own local numbering. Neither check can infer a real upstream deletion if the supposedly consecutive delivery numbers have been reused.

One possible interleaving illustrates the distinction. Suppose the downstream has accepted upstream sequence 550 with consumer delivery number 550. The old leader has emitted further deliveries, including upstream 552 with delivery number 552, but its agreed delivered state only covers upstream 549 / delivery 549. Its remaining packets can still be in flight. A new leader restores that state, redelivers pending upstream 549 with delivery number 550, then delivers upstream 550 with number 551. The redelivery is ignored by the sourcing receiver; the already-stored upstream 550 is suppressed as a duplicate but advances downstream delivery accounting to 551. If the old leader's upstream 552 / delivery 552 arrives before the new leader's upstream 551 / delivery 552, it now looks like a perfectly consecutive delivery with an upstream hole. The mirror records 551 as skipped. When upstream 551 subsequently arrives, it is older than the downstream watermark and is suppressed. There is no protocol error to log: the inputs passed the receiver's continuity test. The stream can keep accepting newer messages and reach the origin's high sequence while retaining an interior hole. This is an example of the permitted ordering, not a claim to have recorded the exact packet order of either reported run.

The origin's intact contents exclude genuine upstream deletion as the explanation for the reported gaps. The false flow-control exception and the receiver continuity rules supply the causal mechanism for that combination of intact origin, interior downstream holes, no error, and continued progress. Comparing only last sequence or lag would miss the loss; counts and deleted-sequence information are essential for a mirror. For a source, compare origin identity/sequence metadata and contents as well as its local sequence state.

There is a second race in the same numbering protocol. `resetStartingSeqLocked` correctly proposed a replicated reset without immediately modifying local delivered or pending state, but it did not prevent `getNextMsg` from selecting more messages before that reset applied. Such selection advances `sseq`, changes redelivery state, and leads to pending-count and delivery updates. Entries produced during that interval can follow the reset entry while carrying the old epoch's delivery numbers. Reset must therefore be a barrier for selection, not merely an eventual assignment of `sseq` and `dseq`. Existing tests that check only that proposing a reset leaves state unchanged do not, on their own, exclude this later selection race.

## Other observations in the maintenance window

* **Ordinary redelivery is not itself data loss.** A legitimate retry can increase the consumer delivery sequence without increasing the original stream sequence. The sourcing receive paths explicitly reject `dc > 1`; their recovery/reset protocol establishes a fresh starting position when continuity is broken. Redelivery can participate in the bad interleaving above by consuming reused delivery numbers, but repeated delivery of an origin message does not delete an interior downstream message. The violated prerequisite is that externally visible delivery numbering lacked a durable quorum record.
* **Ordinary duplicate suppression is not itself data loss.** Suppressing an upstream sequence already stored downstream is required for exactly-once storage across retries. Updating delivery accounting for a consecutive duplicate is also intentional. The defect makes that accounting usable as false evidence of continuity. Suppression of a late missing message after the watermark incorrectly advanced is a consequence of that false continuity decision. Separately, publisher message-id deduplication intentionally stores one copy of a repeated publish with the same id within its configured deduplication window; it neither removes a previously stored interior sequence nor explains two different origin/downstream counts for the same retained origin contents. This repair does not change message-id deduplication.
* **Ordinary acknowledgement lag is not itself data loss.** Acknowledgement state may trail delivered state, leaving pending messages and causing retries. That does not authorize skipping retained origin data. It differs from replication lag in the *delivery* record: the old code could expose a number before that record reached quorum. Flow-control acknowledgements cumulatively acknowledge progress reported by the receiver; after the receiver has falsely advanced its position, they cannot reconstruct the omitted data. Faster acknowledgements or waiting for lag to disappear is no correctness fix.

## Repair and why all its parts matter

The production changes are in `server/consumer.go` and `server/jetstream_cluster.go`. Existing internal names, signatures and fields are retained; reset tracking fields are added. No existing test code or skip condition is changed.

1. Replicated consumers with an acknowledgement policy now use the existing quorum delivery path even when flow control is enabled. `AckNone` and unreplicated immediate delivery retain their existing treatment. Flow control remains active, including its byte window, pending limit, request/reply protocol and heartbeat support. Quorum makes delivery numbers recoverable before they become visible, preventing leadership changes from reusing an exposed but uncommitted number for different data.
2. Flow-control requests wait until queued replicated deliveries have been released. Applying the final queued delivery rechecks whether a request is needed. Otherwise moving just the data behind quorum would let control packets overtake it, asking the receiver to acknowledge bytes/messages that had not yet arrived. Heartbeats are likewise deferred while deliveries await quorum or a reset is pending, so their advertised last-delivery number does not falsely report a gap ahead of queued data. Outstanding flow control still gates delivery normally.
3. Proposing a reset increments a pending-reset counter under the consumer lock. `getNextMsg` returns `errConsumerReset` before accessing the store, redelivery queue or selection state. Pull requests received during the reset receive a 409 error. The delivery loop treats the selection error as a normal wait condition. A final delivery guard also prevents publishing while reset is pending. When a delivery selected before the reset reaches quorum during the barrier, its queued payload is released without sending; the reset will select again from its own starting position. Packets already emitted before the barrier can of course still be in flight. Thus refusal does not advance delivered number, stream selection position, or pending count. A counter covers multiple resets proposed before application, including requests without a reply subject; the reply-tracking map alone would not cover those.
4. Reset application, in Raft log order on every replica, releases its reset barrier and establishes stream position `seq` and next delivery number 1. The existing `store.Reset(seq-1)` records delivered-consumer zero and the corresponding stream starting point, so a subsequent leader restores the reset's numbering. Delivery is signalled again after application. Leadership teardown clears abandoned local pending-reset tracking; an obsolete leader's uncommitted request must not permanently block a later leader.
5. A generation value invalidates a message prepared before a reset or leadership teardown. Replay and rate-limit waits release the consumer lock; checking only whether a reset is *currently* pending would miss a reset that started and completed during such a wait. Such a prepared message is released instead of being delivered with stale reply/sequence information. The reset's own position supplies the subsequent selection.
6. Reset application clears the previous epoch's byte accounting and flow-control reply identity. A delayed response to an old identity cannot acknowledge the new epoch. Flow-control identity validation and its cumulative acknowledgement now run under the same consumer lock, closing the unlock/relock window in which a validated old response could cross a reset. For unreplicated interest/workqueue retention, the associated stream acknowledgement work is collected while locked and executed after unlocking, preserving stream/consumer lock ordering and retention behaviour.

Only changing mirror gap detection would break legitimate upstream deletion/filtering behaviour and would not establish trustworthy consumer numbering. Only removing the flow-control exception would leave reset-era selection and stale prepared deliveries. Only blocking the outer delivery loop would leave direct/internal `getNextMsg` selection able to mutate state. Only checking a pending-reset boolean at send time would miss a completed reset during an unlocked wait. Only delaying flow-control packets, or only clearing byte accounting, would leave the original exposure of uncommitted numbers intact. These changes preserve the protocol's existing continuity assumptions by enforcing them at the producer.

The repair prevents this defect going forward. It does not claim to populate holes already recorded downstream, rewrite stored data, or repair all possible data-loss causes such as configured retention limits. Existing downstream contents remain untouched.

## Why operational shortcuts are not repairs

**Restarting servers:** A restart restores persisted/agreed consumer and stream state. It does not undo downstream skip records or watermarks, and it leaves the faulty delivery path in the binary. Restarting a leader can itself expose the discrepancy between uncommitted deliveries and agreed state. A quiet restart might avoid the race on a particular run, without removing it.

**Purging, truncating, or re-reading downstream:** Purging/truncating destroys or removes downstream contents, violating the requirement to retain stored messages. A complete rebuild might reconstruct a snapshot from an intact origin, but would not fix the consumer protocol and could lose messages again at the next transition. Merely re-reading through the existing sourcing path does not necessarily fill a recorded hole: sequences at or below its accepted watermark are treated as old duplicates. Re-reading is neither a guarantee of in-place repair nor prevention of recurrence. This change deliberately does not use any of these operations.

**Deleting and recreating the consumer:** This abandons durable state and changes the object/numbering epoch. It may temporarily replay retained data if configured to start early enough, but the same flow-controlled replicated delivery code can repeat the failure. It also does not erase the downstream watermark that can reject older sequences. Recreation cannot guarantee recovery of existing holes and violates object continuity.

**Deleting and recreating the mirror or source:** Starting a fresh downstream from a suitable origin position can rebuild retained history, provided the origin still has it. That is replacement, not repair of the same object; it discards existing downstream storage and leaves the broker defect available during subsequent maintenance. A recreation that starts later can simply omit the missing history. None of these procedures meets the stated preservation requirements.

**Turning off consumer flow control:** `AckFlowControl` requires flow control; the configuration checks reject disabling it for this acknowledgement policy. Switching to another policy/consumer or bypassing the durable feed changes the required deployment and can change its acknowledgement and backpressure semantics. Although the old quorum predicate shows why an ordinary acknowledged consumer without flow control avoids that particular exception, disabling flow control does not repair the reset barrier and is not a repair of the required durable flow-controlled path. The corrected path keeps flow control enabled.

## Focused regression evidence

`server/consumer_delivery_reset_regression_test.go` adds two checks without changing existing tests. `TestJetStreamConsumerFlowControlWaitsForDeliveredQuorum` controls application of a delivery proposal: data, flow control and heartbeat output must all remain empty beforehand, then data must precede flow control after application. It also proposes a reset after a delivery is already queued, verifying that applying that delivery does not emit it through the reset barrier. The original immediate-send branch violates the first assertion. `TestJetStreamClusterConsumerResetBlocksSelection` holds the consumer lock across a reset proposal, verifies that selecting a message returns an error without changing stream position, delivery number or pending count, then checks reset state on all three replicas and checks stream sequence 2 / consumer sequence 1 after a leader change. The original unrestricted `getNextMsg` violates the refusal/state assertion.

## Validation and a separate test-fixture timing issue

The repaired production tree passes `GOPROXY=off go build ./...` and `GOPROXY=off go vet ./server`. The existing `TestJetStreamClusterMsgIdDuplicateBug` and `TestJetStreamClusterDuplicateMsgIdsOnCatchupAndLeaderTakeover` also pass, covering origin message-id suppression through maintenance.

The default-scheduler broad run reported only one failing test, `TestJetStreamStreamSourceFromKV`; existing test self-skips were left intact. That test creates a default-history KV bucket and expects both of two immediate updates to the same key to be sourced. Default KV history retains only the latest value: the second update can delete the first update from the origin before the asynchronous sourcing consumer reads it. The failure was `Expected value2, got value3`. A separate diagnostic copy with these production changes reverted reproduced that failure, and isolated repetitions also showed its timing dependence. This is a distinct case from the incident: the incident's origin still retains every missing message. No test code or history setting was changed to accommodate it. Ten isolated repetitions of this unchanged test passed with `GOMAXPROCS=1`; that scheduler setting is used for the complete final selected-suite run, not as a deployment workaround or part of the production repair.

The final selected-suite run completed successfully: **169 top-level tests passed, zero failed, and two existing self-skips remained unchanged**. It used the final production code and both added regression tests. The exact offline build/run commands were:

```sh
GOPROXY=off go test -c ./server -o /app/reset-check.test
GOMAXPROCS=1 /app/reset-check.test \
  -test.run '(Mirror|Source|Sourcing|FlowControl|Consumer.*Reset|Reset.*Consumer)' \
  -test.count=1 -test.timeout=30m -test.v
```

The complete successful test output is `/app/verification-serial.log`; the additional message-id maintenance checks are recorded in `/app/verification-dedupe.log`. The final test selection includes the file-store consumer reset checks, clustered consumer reset checks, mirror/source restart and resynchronization checks, durable sourcing retention checks, and the mirror skip-sequencing regression. Neither the scheduler setting nor the fixture observation changes the production repair or weakens any assertion.
